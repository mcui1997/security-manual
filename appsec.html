Application security

This is where I'm headed, and where the rest of the degree converges. Threat modeling, crypto, PKI, and even the hardware chapter all show up in one place: the code that handles someone else's input.

·
Web SecurityFoundations of IAPKI
Core idea Nearly every serious application vulnerability is one of two mistakes: the application let data be interpreted as code (injection), or the application didn't check whether this user may do this thing to this object (broken access control). Learn to see both and you can review almost anything.

5.1Mistake one: data becomes code

Every interpreter (SQL engine, HTML parser, shell, template engine, LLM) takes one string and splits it into instructions and data. Injection happens when user input gets glued into that string and the interpreter splits it differently than the developer intended. The same bug shows up in every language. Blue is treated as data; red with a dashed outline is parsed as code.

LabOne bug, three interpreterstry the presets, then flip to the fix

The fix is always the same idea: keep code and data in separate channels. Parameterized queries, context-aware output encoding, argument arrays instead of shell strings. LLMs are the uncomfortable exception, because there is no separate channel yet.

That last tab is why this lesson stays current. Prompt injection is injection with no parameterized query. An LLM reads instructions and data as one stream of tokens, so an email, web page, or document it processes can carry instructions. Since you can't reliably separate them, the defense moves to the other principles: least privilege for what the model can do, human confirmation for consequential actions, and treating model output as untrusted input to whatever comes next. (More in Chapter 06.)

5.2Mistake two: nobody checked

Authentication is usually one well-tested library. Authorization is scattered across every endpoint, every object, and every field, and it only takes one missing check. That's why Broken Access Control has been #1 on the OWASP Top 10 since 2021. The classic form is an IDOR (insecure direct object reference), which API security calls BOLA: the app checks that you're logged in, not that the object is yours.

Scanners are bad at finding this because the response is a perfectly valid 200 OK. Finding it takes a human who understands who should see what. It's the strongest argument for manual review and for enforcing authorization centrally (policy engines, framework middleware), not per endpoint.

        


        
5.3The browser's security model in four ideas

        
    
          
  • Same-origin policy (SOP): scripts from evil.com can't read responses from bank.com. It's the foundation, and most web attacks are ways around it.
    • 
          
  • CORS relaxes SOP; it doesn't protect. Access-Control-Allow-Origin: * with credentials, or reflecting any origin, is a vulnerability you configured yourself.
    • 
          
  • XSS defeats SOP from the inside: if attacker script runs on your origin, it can do anything the user can. Defenses: framework auto-escaping, Content-Security-Policy, and HttpOnly cookies to limit what stolen script can take.
    • 
          
  • CSRF rides ambient credentials: the browser attaches cookies automatically, so another site can trigger requests. Defenses: SameSite cookies (now defaulting to Lax in major browsers) and anti-CSRF tokens.
    • 
        


        
5.4Identity: sessions, tokens, OAuth, passkeys

        
Sessions vs. JWTs: a server-side session is a random ID pointing to state on the server, and it's easy to revoke. A JWT is a signed, self-contained claim, which is stateless and scalable but hard to revoke before expiry, and classic bugs live in validation (alg: none, algorithm confusion, not checking aud/exp). OAuth 2.0 is delegated authorization (“let this app read my calendar”). OpenID Connect adds authentication on top (“this is who logged in”). Use the authorization code flow with PKCE; the implicit flow is deprecated. Passkeys (WebAuthn/FIDO2) are public-key crypto bound to the site's origin, which makes them phishing-resistant by design. It's Chapter 04's hostname check, applied to login.

The shared vocabulary of the field. The 2025 edition (finalized early 2026) added two categories, absorbed SSRF into access control, and moved misconfiguration to #2. Know them well enough to explain each in one breath.

        


        
5.6How AppSec actually works: the secure SDLC

        
An AppSec team can't review every line. The job is to put the right control at each stage of how software gets built, so most issues are prevented or caught automatically and humans spend time where judgment matters. “Shift left” means catching things earlier, where they're cheaper to fix. “Shield right” means assuming some will ship and detecting them in production.

Where it breaks
          
    
            
  • Trusting the client: hidden fields, disabled buttons, and client-side validation are UX, not security. Every check must happen on the server.
    • 
            
  • Tool noise: a SAST tool producing 4,000 findings teaches developers to ignore it. A tool nobody trusts is worse than none.
    • 
            
  • Security as a gate at the end: a pentest two weeks before launch finds design flaws when they're most expensive to fix.
    • 
            
  • Dependencies: most of your code is other people's code. Log4Shell (2021) was one library, in a huge share of Java applications, exploitable with a single string. That's injection again (JNDI lookup), inside a supply-chain failure.
    • 
          

        


        
What an AppSec engineer does all week
          
    
            
  • Design reviews and threat models for new features, with the highest leverage and earliest timing.
    • 
            
  • Security code review of risky changes: auth, crypto, file handling, deserialization, anything parsing untrusted input.
    • 
            
  • Running the tooling: SAST, SCA, secrets scanning, DAST, and IaC scanning. Tuning them so the signal is worth a developer's attention.
    • 
            
  • Triage and vulnerability management: is this finding reachable and exploitable? What's the real severity? Who owns the fix, by when?
    • 
            
  • Paved roads: building secure defaults (auth middleware, safe query libraries, hardened templates) so the easy path is the secure path. “Guardrails, not gates.”
    • 
            
  • Pentests and bug bounty: scoping, validating reports, driving fixes.
    • 
            
  • Developer enablement: training, office hours, and good fix guidance in every ticket.
    • 
            
  • AI-era additions: reviewing AI features for prompt injection and excessive agency, and handling the surge of AI-generated code that still needs review.
    • 
          

        


        
Say it in 60 seconds
          
“I see most application vulnerabilities as two root causes. The first is data being interpreted as code: SQL injection, XSS, command injection, and now prompt injection. The fix is keeping code and data in separate channels, like parameterized queries and contextual encoding. The second is missing authorization: the app checks that you're logged in but not that the object is yours. That's why broken access control is number one on the OWASP Top 10, and scanners rarely catch it. As an AppSec engineer, my job is to put the right control at each stage of the SDLC. That means threat modeling at design, secure defaults and review at code, SAST, SCA, and secrets scanning in CI, DAST and pentests before release, and monitoring and bug bounty after. The goal is making the secure path the easy path for developers.”

        


        
Check yourself

        

          
Why do parameterized queries prevent SQL injection when escaping sometimes doesn't?
With parameters, the query structure is sent and parsed first, and the values are bound afterward as pure data, so they can never change the parse tree. Escaping tries to neutralize special characters inside a single string, and it fails when you miss a context, an encoding, or a numeric field without quotes.

          
Stored vs. reflected vs. DOM-based XSS?
Reflected: the payload comes in the request and is echoed back immediately (for example, in a search results page). Stored: the payload is saved (in a comment or profile) and served to every viewer, which makes it the most dangerous. DOM-based: client-side JavaScript takes attacker-controlled data (like location.hash) and writes it into a sink like innerHTML without the server being involved.

          
What's SSRF, and why did OWASP fold it into Broken Access Control?
Server-side request forgery: the attacker makes your server fetch a URL they choose, often an internal one like the cloud metadata service at 169.254.169.254, which can leak credentials (as in the Capital One breach). It's fundamentally an access-control failure, because the server's network position is being used on behalf of someone who shouldn't have it. Mitigate with outbound allowlists, blocking internal ranges, and IMDSv2.

          
SAST vs. DAST vs. SCA: what does each find and miss?
SAST reads source code. It's early and precise about location but noisy and blind to runtime config. DAST attacks the running app. It sees real behavior but has poor coverage and can't point to the line. SCA inventories dependencies against known CVEs. It's essential for supply chain, but reachability matters. None of them reliably find business-logic or authorization flaws; that takes humans.

          
You get a critical finding the week of a launch. What do you do?
Validate that it's real and reachable. Assess actual impact in context. Look for a quick compensating control (feature flag, WAF rule, config change) that lets launch proceed safely. If none exists, bring the risk to the business owner in business terms and let them make an informed decision that gets recorded. Then make sure the real fix is scheduled and tracked. The role is to inform the risk decision, not to be the department of no.
