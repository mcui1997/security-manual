AI: tool & target

Two courses and my biggest project live here. AI shows up in security twice: as a tool defenders use to see more than humans can, and as a target, a new kind of software with its own attack surface. You need both views at once.

Core idea ML is a pattern-matcher that scales far beyond human attention, but it's statistical, brittle at the edges, and trained on the past, while attackers adapt. So it's a force multiplier for analysts, not a replacement. And the moment you deploy a model, the model, its data, and its pipeline become attack surface.

6.1AI as a tool: where ML earns its place

Security produces more data than any team can read: billions of log lines, packets, binaries, and emails. ML is good wherever a human expert could decide but can't do it a million times a day: spam and phishing filtering, malware family classification, network intrusion detection, user-behavior anomalies (UEBA), and alert triage. Two broad styles:

  • Supervised (learn from labeled examples): accurate on known threats, blind to genuinely new ones, and only as good as its labels.
  • Unsupervised / anomaly detection (learn “normal,” flag deviations): can catch the novel, but “unusual” isn't the same as “malicious,” so it's noisy.

The single most important number in applied security ML isn't accuracy. It's the base rate. Attacks are rare, so even a very good detector can bury a SOC in false alarms. Play with it:

6.2My project: From Packets to Pixels

From Packets to Pixels: A Vision Transformer & Few-Shot Learning Approach to Malicious Network Threat Detection

Stein, Price, Donato, Ontiveros Garcia, Cui, Watkins. Johns Hopkins University, Department of Computer Science.

The problem: classify network traffic as benign or as a specific malware family, including families the model has barely seen, using the CIC-IoT23 malware-traffic dataset. IoT networks were the setting because the devices are always on, rarely patched, and a favorite target for botnets.

The idea in three moves

  1. Transformers see globally, but bytes make sequences too long. CNNs and LSTMs capture local byte patterns well but struggle with dependencies that span a whole packet or flow. Transformers use self-attention, so every position can attend to every other from the first layer. But if every byte is a token, a packet becomes a very long sequence, and attention cost grows with the square of the sequence length.
  2. So we made packets into images. We grouped contiguous byte segments into fixed-size patches and arranged them on a 2D grid, a “packet image.” Each patch becomes one token for a Vision Transformer (ViT). The sequence gets dramatically shorter, and the ViT still attends across the entire packet.
  3. New malware shouldn't require retraining. We used the trained ViT as a feature extractor and added a few-shot learning module, so the system can adapt to a new malware class from only a handful of labeled examples. That matters because attackers ship new variants constantly and labeled data is scarce.

Result: strong accuracy across multiple malware families on CIC-IoT23, outperforming the baseline methods we compared against.

Few-shot: learning a new family from five examples

A classifier with a fixed output layer can only name classes it was trained on. Few-shot learning changes the question from “which of my N classes is this?” to “which of these examples is this most similar to?” The ViT maps each packet image to an embedding vector, a point in a learned space where similar traffic clusters together. A new family only needs a few labeled examples (the support set) to define its region of that space. A common approach is to average them into a prototype and assign each new sample to the nearest one. Click anywhere to drop a new packet's embedding:

Adding a class costs five labeled samples and zero retraining. The embedding's quality does the heavy lifting, which is why a strong backbone (the ViT) matters. Security catch: an attacker who can craft traffic that lands near the “benign” prototype evades detection (6.4).

6.3MLOps: the model is the easy part

AI/ML Ops reframed everything. A notebook with 97% accuracy is a demo. A model in production is a system: data pipelines, feature stores, training jobs, a model registry, serving infrastructure, and monitoring for drift, when real-world data slowly stops looking like the training data. In security, drift isn't just gradual. It's adversarial, because attackers change their behavior specifically to evade you. And every box in that pipeline is something an attacker can target:

6.4AI as a target

Adversarial ML has four classic attack families, catalogued in MITRE ATLAS (ATT&CK for AI systems):

  • Evasion: craft inputs the model misclassifies. Tiny perturbations fool image models; for my packet detector, it would mean padding or reshaping malicious traffic until it embeds near “benign.” Detectors meet an adaptive adversary, not a static test set.
  • Poisoning: corrupt the training data so the model learns a blind spot or a backdoor trigger. It's dangerous in security because training data often comes from the very environment the attacker is in.
  • Extraction: query a model enough to clone it, then craft evasions offline.
  • Inference: learn private facts about the training data (membership inference, or regurgitation of memorized secrets).

LLM applications added a new layer, catalogued in the OWASP Top 10 for LLM Applications (2025). It starts with LLM01 Prompt Injection and includes sensitive information disclosure, supply chain, data and model poisoning, improper output handling, excessive agency, system prompt leakage, vector/embedding weaknesses, misinformation, and unbounded consumption. The throughline is Chapter 05's lesson. The model can't separate instructions from data, so security has to come from the system around it: least-privilege tools, human approval for consequential actions, output treated as untrusted, and isolation of untrusted content. Agents that take real actions make this the fastest-moving area of AppSec.

Where it breaks
  • Benchmark ≠ battlefield: high accuracy on a static dataset (including public ones like CIC-IoT23) says little about an adversary adapting to your model.
  • Base rates: a detector that floods analysts with false positives gets turned off, which is the same as no detector.
  • Unexplainable verdicts: analysts can't act on “the model says 0.93.” Attention maps and nearest-neighbor examples help build trust.
  • Loading untrusted model files: Python pickle deserialization executes code. Prefer safetensors, and scan and pin models from public hubs.
  • LLM features with too much agency: a summarizer that can also send email is an injection waiting to happen.
On the job (AppSec)
  • Reviewing AI features is now a core AppSec task: map the tools and data the model can reach, look for prompt-injection paths, and enforce authorization on tool calls with the user's permissions, not the service's.
  • ML supply chain: model provenance, signed artifacts, dependency scanning for ML stacks, secrets in notebooks.
  • Using AI defensively: LLM-assisted code review, triage, and threat modeling. Useful, but verify, because it inherits the base-rate problem.
  • Frameworks to name-drop accurately: OWASP LLM Top 10, MITRE ATLAS, NIST AI RMF.

Check yourself

Why a Vision Transformer on packets instead of a CNN or LSTM?

CNNs capture local patterns and LSTMs process sequences step by step; both struggle with long-range dependencies across a packet or flow. Transformers attend globally from the first layer, but per-byte tokens make sequences long, and attention is quadratic in length. Patching bytes into a 2D image cuts the token count while keeping global attention, and it lets us use a mature vision architecture.

What is few-shot learning, and why does it matter for security?

Classifying new classes from a handful of labeled examples, typically by comparing embeddings (for example, nearest prototype) instead of retraining an output layer. It matters because new malware families appear constantly and labeled data for them is scarce at exactly the moment you need it.

A detector has 99% recall and a 1% false-positive rate. Is it good?

It depends on the base rate. If 1 in 10,000 events is malicious, then per million events you'd get about 99 true alerts and about 10,000 false ones, so under 1% of alerts are real. Whether that's usable depends on analyst capacity and what the alerts feed into.

How would you secure an LLM feature that can read email and send messages?

Assume every email can carry prompt injection. Split capabilities: the reading/summarizing path gets no send tools. Require explicit user confirmation for sends, with the actual content shown. Enforce the user's own permissions on every tool call. Filter and validate outputs before they reach other systems. Log tool invocations and rate-limit them. Red-team with indirect injection payloads.
