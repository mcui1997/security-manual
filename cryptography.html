Cryptography

Cryptology was the most mathematical course in the degree. What's left after the modular arithmetic fades: a clear sense of what each primitive promises, what it doesn't, and why real-world crypto almost never fails at the math.

Core idea Cryptography doesn't make a security problem go away. It turns a big problem (protect all this data) into a small one (protect this key). The small problem is still a problem, and that's where crypto actually fails.

3.1The toolbox, by what it guarantees

The most useful way to hold crypto in your head isn't by algorithm. It's by property. When someone says “we encrypt it,” the right question is: which guarantee did you need, and does that primitive actually give it?

3.2Symmetric vs. asymmetric, and why we use both

Symmetric crypto (one shared key) is fast and strong but has a distribution problem: how do two strangers get the same secret? Asymmetric crypto (public/private key pairs) solves distribution with math that's easy one way and hard the other (Chapter 01's hardness again), but it's slow. So real protocols are hybrid: asymmetric crypto agrees on or wraps a symmetric key, and the symmetric key protects the bulk data. TLS, Signal, PGP, and cloud KMS “envelope encryption” all follow this pattern.

3.3What “good” looks like: the avalanche

A good hash or cipher behaves like a random function: change one input bit and about half the output bits flip, unpredictably. That's what makes it impossible to work backwards or nudge an output toward a target. Change one character below and count.

A hash alone is not authentication. An attacker who changes the message just recomputes the hash. For that you need a key: an HMAC or a signature.

3.4Strong algorithm, wrong use: the ECB penguin

AES is unbroken. You can still use it in a way that leaks everything. In ECB mode each 16-byte block is encrypted independently, so identical plaintext blocks produce identical ciphertext blocks. The lesson generalizes. Crypto libraries hand you sharp tools, so the safe move is a high-level API that picks the mode for you (libsodium, Google Tink, or your platform's AEAD). Never reach for raw block-cipher primitives.

3.5The real problem: keys

Once the algorithm is sound, every serious question is about keys. Where are they generated, and with what randomness? Where do they live? Who and what can use them? How are they rotated, and how are they revoked if they leak? That's key management, and it's where the industry has converged on a few patterns:

  • HSMs and cloud KMS: the key never leaves tamper-resistant hardware. You send data in and get results out, and every use is logged.
  • Envelope encryption: a data key encrypts the data, a master key in KMS encrypts the data key. Rotating the master doesn't mean re-encrypting petabytes.
  • Secrets managers: Vault, AWS Secrets Manager, and the like replace keys in config files and environment variables, with rotation and audit.
  • Crypto agility: design so the algorithm can be swapped without a rewrite. This was an abstract virtue until post-quantum migration made it a deadline (Chapter 09).
Where it breaks
  • Hard-coded or committed keys: the most common crypto failure by far. No math required.
  • Nonce reuse: reusing a nonce with AES-GCM leaks the XOR of plaintexts and lets attackers forge messages. It's catastrophic, not gradual.
  • Bad randomness: Debian's 2008 OpenSSL bug cut the keyspace to about 32,768 possible keys per key type. Every key generated on those systems for nearly two years was guessable.
  • Fast hashes for passwords: SHA-256 is designed to be fast, and GPUs try billions per second. Passwords need slow, salted, memory-hard functions.
  • Side channels: comparing MACs with == leaks timing, so use constant-time comparison. Padding oracles turned error messages into decryption.
  • Rolling your own: the rule isn't “never write crypto code.” It's “never invent a scheme or compose primitives yourself when a vetted construction exists.”
On the job (AppSec)
  • Code review: flag ECB, MD5/SHA1 for security use, static IVs, Math.random() for tokens, == on MACs, and homemade JWT verification.
  • Password storage: Argon2id or bcrypt with a sensible cost. Know the OWASP Password Storage Cheat Sheet exists.
  • Secrets: secret scanning in CI (gitleaks, GitHub push protection), rotation runbooks, and responding when a key leaks.
  • OWASP A04:2025, Cryptographic Failures: this whole chapter is that category.
Say it in 60 seconds

“I think about crypto by property: confidentiality, integrity, authenticity, non-repudiation. Then I ask which primitive actually provides the one we need. A hash isn't authentication, and encryption without an AEAD mode isn't integrity. Real systems are hybrid: asymmetric crypto establishes a key, symmetric AEAD protects the data, and signatures plus certificates tie keys to identities. The math is almost never what breaks. It's misuse, like ECB mode, nonce reuse, fast password hashes, and bad randomness, and above all key management. Crypto turns a data-protection problem into a key-protection problem.”

Check yourself

What's the difference between hashing, encryption, and encoding?

Encoding (Base64) is reversible by anyone and provides no security. Encryption is reversible only with a key and provides confidentiality. Hashing is one-way and provides a fingerprint for integrity. Add a key (HMAC) and you get authenticity too.

Why can't you just SHA-256 passwords with a salt?

A salt stops precomputed rainbow tables, but SHA-256 is fast, so an attacker with a GPU can still try billions of guesses per second against each salted hash. Password hashing should be deliberately slow and memory-hard (Argon2id, scrypt, bcrypt) to make each guess expensive.

MAC vs. digital signature: when do you need which?

A MAC uses a shared symmetric key, so it's fast and fine when both parties trust each other (like webhook verification). But either party could have produced it, so there's no non-repudiation. A signature uses a private key only the signer holds, so anyone with the public key can verify it, and the signer can't deny it. Use signatures for software updates, certificates, and legal records.

What is forward secrecy and why does TLS 1.3 require it?

Each session uses ephemeral key-exchange keys that are thrown away afterward. If the server's long-term private key is stolen later, past recorded sessions still can't be decrypted. TLS 1.3 removed static RSA key exchange for exactly this reason.
