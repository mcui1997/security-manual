How machines really work

I won't remember how to balance a red-black tree. I do remember that every system is a stack of abstractions, and that attackers make a living in the gaps between them.

Core idea Software is a promise made by an abstraction. Security bugs happen where the promise and the machine disagree: where the programmer thinks “this is a name” and the CPU sees “these are bytes, and the next ones are a return address.”

1.1A stack of promises

The four bridge courses looked unrelated at the time. Put together, they describe one tower. Java taught the top: objects, types, and a runtime that checks array bounds for you. Computer Organization taught the bottom: registers, memory addresses, and an instruction cycle that fetches whatever bytes the program counter points to. Data Structures and Algorithms sat in the middle and taught that how you organize data decides what the system is good at, bad at, and vulnerable to.

Each layer hides the layer below it. That's why abstraction works, and it's also why abstraction leaks. A web developer thinks in strings. A database thinks in parsed queries. The OS thinks in pages and permissions, and the CPU thinks in speculative micro-operations. Every famous attack class is really a layer boundary where one side's assumptions didn't hold on the other side.

1.2Memory: where data becomes control

Computer Organization's most security-relevant lesson is that code and data live in the same memory. That's the von Neumann design. When a C function runs, its local variables sit on the stack right next to bookkeeping the CPU relies on, including the return address: where to jump when the function finishes. If a program copies input into a fixed-size buffer without checking the length, the extra bytes don't vanish. They overwrite whatever comes next.

Real exploits put an address in those red cells that points back into attacker-controlled bytes. Modern mitigations (canaries, ASLR, non-executable stacks) raise the cost. Memory-safe languages remove the bug class.

That one mechanism accounts for a remarkable share of the worst vulnerabilities ever found. Microsoft and the Chromium project have both reported that roughly 70% of their serious security bugs are memory-safety issues. That's why CISA, the NSA, and the big vendors now push memory-safe languages (Rust, Go, Java, C#) for new code. The Java course's “boring” bounds check, the ArrayIndexOutOfBoundsException, is a security control.

1.3Data structures under an adversary

Data Structures gets taught as a performance topic: pick the right structure and get O(1) lookups. The security version of that lesson: your average case is my attack surface. Complexity analysis usually assumes friendly input. An attacker chooses the worst case on purpose.

  • Hash tables → HashDoS. A hash table is O(1) until every key lands in the same bucket, and then it's O(n). In 2011, researchers showed that one crafted POST body could pin a web server's CPU across many languages' frameworks. The fix was randomized (keyed) hash functions, which is a crypto idea used to defend a data structure.
  • Regex → ReDoS. Backtracking regex engines can go exponential on crafted input. One bad pattern in a validation routine can take down a service.
  • Trees of hashes → integrity at scale. Merkle trees let you prove that one item belongs to a huge set without shipping the whole set. They're the backbone of Git, Certificate Transparency logs (Chapter 04), and software supply-chain systems like Sigstore.

1.4Hardness is the foundation

Foundations of Algorithms ended in complexity theory: P, NP, and the idea that some problems have no known efficient solution. It felt abstract. It's actually the load-bearing wall of modern security. Cryptography is engineered asymmetry: an operation that's cheap one way (multiply two primes, hash a password) and believed infeasible the other way (factor the product, invert the hash).

“Infeasible” is a statement about exponential growth. Each added bit of key doubles the attacker's work. Slide it and watch:

DES (56-bit) fell to purpose-built hardware in 1998. AES-128 is out of reach of any conceivable classical computer. Chapter 09 covers what Grover's algorithm does to this curve (it roughly halves the bits) and what Shor's does to RSA (it breaks it outright).

That's the thread from this chapter to the frontier. Security built on hardness assumptions is only as durable as the assumptions. Quantum computing doesn't make math easier in general. It makes specific problems (factoring, discrete logarithms) easy, and those are exactly the ones public-key crypto depends on.

Where it breaks
  • Leaky abstractions: developers trust the layer below to behave as documented. Speculative execution (Spectre) broke that assumption in hardware itself.
  • Unsafe languages at trust boundaries: C/C++ parsers handling untrusted input (images, fonts, network packets) are historically the richest source of remote code execution.
  • Average-case thinking: designing for typical input when an adversary controls the input.
On the job (AppSec)
  • You read code in languages you don't write daily. The Java course's value is being able to trace data through a system: where does this input go, and what touches it?
  • Memory-safety bugs show up in SAST findings, fuzzing crashes, and dependency CVEs. You triage them by asking whether attacker-controlled data reaches the unsafe operation.
  • Denial-of-service reviews: unbounded loops, regexes, recursion, and collection sizes on untrusted input.
Say it in 60 seconds

“The bridge courses gave me a mental model of the full stack, from Java objects down to registers and memory. The security payoff is understanding why attacks work, not just that they do. A buffer overflow is data spilling into control information, because code and data share memory. Denial-of-service bugs are often an attacker forcing the worst case of a data structure. And crypto rests on complexity: problems that are cheap in one direction and infeasible in the other. That last point is why quantum matters, because it makes specific hard problems easy.”

Check yourself

Why are memory-safety bugs so dangerous compared with other bugs?

They let an attacker write outside the intended data region, into control data like return addresses, function pointers, or vtables. That can turn a crash into arbitrary code execution. Most other bugs corrupt a value; these can hijack the program's control flow.

What do stack canaries, ASLR, and DEP/NX each do?

Canary: a secret value placed before the return address, checked before returning, so overwrites are detected. ASLR: randomizes where code and data load, so the attacker doesn't know which address to jump to. DEP/NX: marks the stack and heap non-executable, so injected bytes can't run directly. Attackers respond with information leaks and return-oriented programming (ROP). Mitigations raise cost; they don't remove the bug.

Give an example of algorithmic complexity as a security issue.

HashDoS: colliding keys turn O(1) hash table inserts into O(n), so n inserts cost O(n²). Or ReDoS: catastrophic backtracking in a regex. The fix is to bound input sizes and use randomized hashing or linear-time regex engines.

Why does adding one bit to a key double the brute-force cost?

The keyspace is 2n. Adding one bit makes it 2n+1 = 2 × 2n. That exponential growth is why 128-bit symmetric keys are safe against classical brute force.
