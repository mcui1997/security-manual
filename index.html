The one-sentence version Security is the discipline of finding the places where a system trusts something it shouldn't (an input, a key, a certificate, a model, an assumption) and deciding, at a cost the business can accept, what to do about it.

How to use this

  1. Full refresh (≈60 min). Read chapters 01–09 in order. Each one follows the same shape: the core idea, the architecture, where it breaks, how it shows up on the job, and a 60-second version to say out loud.
  2. Quick refresh (≈10 min). Read only the green “Say it in 60 seconds” box in each chapter.
  3. Before an interview (≈20 min). Go to Interview mode. Practice the 2-minute story out loud, then work through the flashcards until none of them surprise you.
  4. Touch the labs. Every chapter has at least one interactive visual. Poke at them. They exist because I remember mechanisms I've played with better than paragraphs I've read.

Five ideas that run through everything

The courses were taught one at a time, but they are really variations on a few themes. Click an idea to see where it shows up across the chapters.

①

Trust boundaries

Every serious vulnerability is a place where something untrusted crosses into a trusted zone without being checked. Find the boundaries and you've found the attack surface.

②

Data must not become code

Buffer overflows, SQL injection, XSS, and prompt injection are one mistake in four costumes: the system let input be interpreted as instructions.

③

Everything rests on assumptions

“Factoring is hard.” “The hardware does what the code says.” “The model behaves like it did in testing.” Security work means naming the assumption and asking what happens when it fails.

④

The strong part rarely breaks

AES doesn't get broken. Keys leak, certificates expire, pipelines get poisoned, and access checks get forgotten. The failures live in the system around the strong component.

⑤

Security is risk, not perfection

Nothing is “secure.” It's secure enough, against a specific adversary, at an acceptable cost. That's how you decide what to fix first and how you explain it to the people who fund it.
